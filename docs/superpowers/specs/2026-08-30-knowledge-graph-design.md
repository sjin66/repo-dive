# Knowledge Graph Technical Specification

**Status:** Draft for review
**Date:** 2026-08-30
**Schema:** Knowledge Graph 1.0
**Depends on:** repo-dive index, retrieval, context, and artifact storage contracts
**Product requirements:** `2026-08-30-knowledge-graph-prd.md`

## 1. Objective

Add a deterministic, local Knowledge Graph pipeline to repo-dive without moving interpretation or prose generation into the CLI.

The design creates three strictly separated layers:

```text
Index facts                 Agent semantics              Published projections
files/symbols/edges   ->    labels/summaries/meaning -> architecture/flows/tour/wiki topics
deterministic               evidence-cited               deterministic assembly
```

The public artifact explains what is known, where it came from, which parts were generated by a calling agent, and whether each part is current.

## 2. Assumptions

1. Knowledge Graph support is additive and optional.
2. The current private SQLite index remains the source of structural facts.
3. Existing `GraphReader`, `SymbolGraph`, `IndexStore`, `EvidencePacker`, and Wiki state patterns are reused through narrow interfaces.
4. The CLI never invokes a generative model.
5. JSON is the only Version 1 publication format; Markdown remains a command rendering option for summaries.
6. Wiki Schema 2.0 does not consume graph projections automatically.
7. No runtime dependency is added for graph storage, clustering, visualization, or graph queries.

## 3. Capability Map

This initiative contains independently testable capabilities. The module IDs below are stable review keys.

| Module ID | Responsibility | Depends on |
|---|---|---|
| `graph-contracts` | Versioned immutable models, IDs, validation, error codes | existing parsing/index contracts |
| `graph-materialization` | Index inventory, bounded fact graph, components, flow candidates | `graph-contracts` |
| `graph-evidence` | Per-unit queries, required Evidence, snapshots, budgets | `graph-materialization`, existing retrieval/context |
| `graph-semantics` | Agent submission decoding, citation validation, state transitions | `graph-evidence` |
| `graph-projections` | Architecture, flow, reading-tour, and Wiki-topic views | `graph-semantics` |
| `graph-cli` | Non-interactive commands, JSON envelopes, exit codes | all provider modules |

Build order:

```text
graph-contracts
  -> graph-materialization
  -> graph-evidence
  -> graph-semantics
  -> graph-projections
  -> graph-cli
```

The modules are logical capability boundaries. They may share the `src/repo_dive/knowledge/` package, but imports must follow the dependency direction above.

## 4. System Context and Ownership

### 4.1 Existing owners

| Concern | Owner | Knowledge Graph access |
|---|---|---|
| Repository traversal | `scanner` | No direct traversal; consume published index inventory |
| Language parsing | `parsing` | Read normalized symbols and relationships only |
| SQLite schema and queries | `indexing` | Use `GraphReader`/`IndexStore` interfaces; no raw SQL |
| Candidate ranking | `retrieval` | Supply bounded Evidence candidates |
| Token budgeting | `context` | Reuse `EvidencePacker` behavior |
| Wiki templates and pages | `wiki` | No dependency on Knowledge Graph in Version 1 |
| CLI rendering | `cli.py` and command adapters | Domain objects contain no terminal concerns |

### 4.2 New owner

`src/repo_dive/knowledge/` owns:

- public Knowledge Graph models and decoders;
- deterministic graph materialization;
- semantic work-unit state;
- graph Evidence snapshots;
- semantic submission validation;
- graph projections;
- graph artifact persistence orchestration.

It must not depend on terminal rendering, environment lookup, a concrete embedding provider, or a model SDK.

### 4.3 Dependency rule

```text
commands/graph.py
    -> knowledge/service.py
        -> knowledge/{materializer,evidence,semantics,projections,store}.py
            -> indexing/retrieval/context/storage public interfaces
```

No reverse dependency from `indexing`, `retrieval`, or `context` to `knowledge` is allowed.

## 5. End-to-End State Flow

```text
NO_STATE
   |
   | graph init
   v
FACTS_READY
   |
   | graph evidence --unit U
   v
U:EVIDENCE_READY
   |
   | calling agent produces unit.json
   | graph unit --unit U --input unit.json
   v
U:GENERATED
   |
   | repeat for required units
   v
SEMANTICS_READY
   |
   | graph validate
   v
VALID
   |
   | graph build
   v
PUBLISHED
```

On index change, each unit is independently re-evaluated:

```text
referenced facts unchanged + Evidence hash unchanged -> preserve GENERATED
referenced facts or Evidence changed                 -> STALE
unit no longer exists                                -> remove from working state, retain no projection
new unit                                             -> PENDING
```

Publication is prohibited while a required unit is `pending`, `evidence_ready`, `stale`, or `failed`.

## 6. Artifact Layout

Knowledge Graph files are isolated from Wiki artifacts:

```text
.repo-dive/
├── knowledge-graph.json              # stable, last valid public artifact
├── graph/
│   ├── state.json                    # resumable working state
│   └── metadata.json                 # source/build identity and hashes
├── wiki.md
├── wiki.json
├── metadata.json
└── index/
```

Rules:

- `knowledge-graph.json` is replaced atomically only by `graph build`.
- `graph/state.json` may contain incomplete unit state but must always be schema-valid.
- `graph/metadata.json` is graph-specific and must not overload Wiki metadata.
- Temporary files use the existing storage abstraction and are never public contracts.
- repo-dive never edits the analyzed repository's `.gitignore`.

## 7. Data Contract

### 7.1 Top-level published artifact

```json
{
  "schema_version": "1.0",
  "source": {
    "repository_fingerprint": "sha256:...",
    "index_build_id": "...",
    "index_schema_version": "...",
    "source_control": {
      "kind": "git",
      "commit": "...",
      "is_dirty": false
    }
  },
  "generation": {
    "node_budget": 10000,
    "edge_budget": 30000,
    "node_count": 4120,
    "edge_count": 12844,
    "omitted_node_count": 0,
    "omitted_edge_count": 0,
    "truncated": false,
    "content_hash": "sha256:..."
  },
  "facts": {
    "nodes": [],
    "edges": []
  },
  "semantics": {
    "units": []
  },
  "views": {
    "architecture": {},
    "flows": [],
    "reading_tour": {},
    "wiki_topics": []
  }
}
```

Unknown top-level or nested fields are rejected in Schema 1.0. Future additive fields require a schema-version update and decoder tests.

### 7.2 Source identity

`repository_fingerprint` is the authoritative freshness key. Git metadata is descriptive and may be absent outside Git repositories. Timestamps are excluded from content hashes and deterministic output.

### 7.3 Fact node

```json
{
  "id": "symbol:8a61...",
  "kind": "symbol",
  "symbol_kind": "class",
  "name": "WikiService",
  "qualified_name": "repo_dive.wiki.service.WikiService",
  "path": "src/repo_dive/wiki/service.py",
  "range": {
    "start_line": 267,
    "end_line": 741
  },
  "index_symbol_id": "...",
  "attributes": {
    "language": "python",
    "is_entrypoint": false,
    "is_test": false
  }
}
```

Allowed node kinds:

- `repository`;
- `file`;
- `symbol`.

The schema deliberately excludes agent concepts from `facts.nodes`.

ID rules:

- repository root: `repository:root`;
- file: `file:` plus SHA-256 of the repository-relative POSIX path;
- symbol: `symbol:` plus SHA-256 of path, qualified name, kind, and a deterministic collision discriminator;
- `index_symbol_id` preserves the link to the private index but is not the public identity.

Line movement alone should not change a public symbol ID unless it resolves an otherwise ambiguous collision. The materializer must detect collisions and use a stable source-order discriminator.

### 7.4 Fact edge

```json
{
  "id": "edge:42d0...",
  "source_id": "symbol:...",
  "target_id": "symbol:...",
  "kind": "calls",
  "origin": "parser",
  "confidence": 1.0,
  "provenance": {
    "path": "src/repo_dive/wiki/service.py",
    "start_line": 526,
    "end_line": 526,
    "precision": "definition"
  }
}
```

Allowed edge kinds in Version 1:

- `contains`;
- `imports`;
- `calls`;
- `inherits`;
- `depends_on`.

Allowed origins:

- `parser`: normalized from a parser relationship;
- `derived`: computed deterministically from parser facts.

`agent` is not a valid fact-edge origin. Agent-created relationships belong to semantic units.

Provenance precision:

- `exact`: parser reported the relationship source location;
- `definition`: source symbol definition range is the best available locator;
- `inferred`: deterministic aggregation or topology rule; the derivation rule is included in attributes.

### 7.5 Component candidate

A component is a deterministic semantic work scope, not an agent-invented cluster.

```json
{
  "id": "component:91af...",
  "scope": "src/repo_dive/wiki",
  "member_node_ids": ["file:...", "symbol:..."],
  "incoming_component_ids": ["component:..."],
  "outgoing_component_ids": ["component:..."],
  "derivation": {
    "rule": "package_scope_v1",
    "signals": ["python_package", "cross_file_relationships"]
  },
  "membership_hash": "sha256:..."
}
```

Version 1 grouping order:

1. parser-recognized package/module scope;
2. manifest or configured source-root scope from deterministic classification signals;
3. top-level directory scope;
4. repository root fallback.

No stochastic clustering is used. Empty or single-file repositories still produce one component.

### 7.6 Flow candidate

```json
{
  "id": "flow:4da7...",
  "root_node_id": "symbol:...",
  "step_node_ids": ["symbol:..."],
  "edge_ids": ["edge:..."],
  "is_truncated": false,
  "derivation": {
    "rule": "entrypoint_traversal_v1",
    "max_depth": 6
  },
  "membership_hash": "sha256:..."
}
```

Flow roots come only from deterministic registered signals, such as executable manifests, framework entrypoint registries, CLI command handlers, or explicitly indexed public entrypoints. If no supported root is found, the graph contains no flow unit and reports the missing signal; it must not guess from names alone.

Traversal uses stable breadth-first ordering, allowed edge kinds, minimum confidence, maximum depth, and the global node/edge budgets.

### 7.7 Semantic unit

```json
{
  "id": "unit:component:91af...",
  "kind": "component",
  "subject_id": "component:91af...",
  "status": "generated",
  "evidence_snapshot_id": "evidence:...",
  "membership_hash": "sha256:...",
  "submission_hash": "sha256:...",
  "content": {
    "title": "Governed Wiki pipeline",
    "summary": "Validates repository classification, Evidence, page state, and final Wiki assembly.",
    "responsibilities": [
      {
        "text": "Persists page-scoped Evidence before accepting generated Markdown.",
        "evidence_ids": ["E1", "E4"]
      }
    ],
    "concepts": [
      {
        "id": "concept:evidence-gate",
        "label": "Evidence gate",
        "description": "...",
        "fact_node_ids": ["symbol:..."],
        "evidence_ids": ["E1"]
      }
    ],
    "relationships": [
      {
        "source_concept_id": "concept:evidence-gate",
        "target_concept_id": "concept:page-state",
        "kind": "enables",
        "description": "...",
        "evidence_ids": ["E1", "E2"]
      }
    ]
  }
}
```

Semantic relationship kinds are descriptive and separate from parser edges:

- `enables`;
- `orchestrates`;
- `validates`;
- `persists`;
- `transforms`;
- `guards`;
- `explains`.

The fixed registry prevents arbitrary relation strings from becoming an accidental API. Extending the registry is additive within a compatible minor schema only when consumers are documented to handle unknown enum values; otherwise it requires a schema bump.

### 7.8 Evidence snapshot

The state artifact persists a graph-specific Evidence snapshot with:

- schema version;
- repository fingerprint and index build ID;
- unit ID and membership hash;
- query plan and stable query hash;
- token budget and actual token count;
- ordered Evidence items;
- required/supplemental role for each item;
- snapshot content hash.

Each Evidence item uses the existing repository-relative path, one-based inclusive range, symbol metadata, complete source chunk, and stable Evidence ID contract.

## 8. Deterministic Materialization

### 8.1 Required index interfaces

Knowledge Graph code must not enumerate SQLite tables directly. `indexing` must expose bounded methods equivalent to:

```python
class KnowledgeGraphReader(GraphReader, Protocol):
    def count_symbols(self) -> int: ...
    def count_relationships(self) -> int: ...
    def list_files(self, *, limit: int, offset: int = 0) -> tuple[IndexedFile, ...]: ...
    def list_symbols(self, *, limit: int, offset: int = 0) -> tuple[Symbol, ...]: ...
    def list_relationships(
        self,
        *,
        limit: int,
        offset: int = 0,
    ) -> tuple[Relationship, ...]: ...
```

Requirements:

- calls are bounded;
- ordering is stable and documented;
- the interface returns immutable domain values;
- pagination cannot skip or duplicate records within one published index build;
- the reader exposes the current source/build identity.

### 8.2 Inclusion order under budgets

The materializer uses a deterministic priority tuple, not a floating-point opaque score:

1. repository root;
2. all file nodes, ordered by path, while budget permits;
3. entrypoint symbols;
4. symbols referenced across files, ordered by descending cross-file fan-in then stable identity;
5. remaining symbols, ordered by path, start line, kind, qualified name;
6. fact edges whose endpoints are included, ordered by source ID, kind, target ID, origin.

If the node budget cannot include the repository root and at least one file node, initialization fails with `graph_budget_insufficient`. Otherwise it publishes a visibly truncated working graph.

Edge inclusion never introduces dangling endpoints. Omitted-edge counts distinguish:

- `endpoint_omitted`;
- `edge_budget_exhausted`;
- `unsupported_relationship_kind`.

### 8.3 Component derivation

Component scope is selected using deterministic repository classification and topology signals. Membership is the union of files under the scope and their included symbols. Component dependencies aggregate included fact edges crossing component boundaries.

An aggregated `depends_on` edge records:

- source and target component IDs;
- contributing fact edge IDs;
- contribution count;
- maximum and minimum confidence;
- derivation rule version.

### 8.4 Flow derivation

For each supported entrypoint root:

1. traverse allowed `calls`, `imports`, and `contains` edges;
2. cap depth per the registered flow rule;
3. avoid revisiting a node;
4. use stable neighbor ordering;
5. retain the predecessor edge for each step;
6. record truncation and terminal reasons.

The CLI does not claim that a static call graph is a complete runtime trace. Published flow metadata calls it a `static_flow` and exposes confidence and coverage.

## 9. Evidence Collection

Command:

```bash
repo-dive graph evidence <repository> \
  --unit <unit-id> \
  --token-budget <tokens> \
  --max-results <count> \
  --format json
```

Required Evidence is selected before supplemental Evidence:

- component unit: representative definitions for every direct member file selected by the deterministic representative rule;
- flow unit: the root and every included step definition;
- reading-tour unit: representative definitions for every tour stop;
- repository summary unit: one representative per non-empty component.

If required complete chunks do not fit, return exit `2` with `graph_required_evidence_budget` and include `required_tokens` and `provided_tokens` in the error details. Do not persist a snapshot.

Supplemental retrieval uses the existing search/fusion pipeline with a deterministic query assembled from unit facts. It cannot displace required Evidence.

## 10. Agent Generation Contract

The CLI response from `graph evidence` includes a `generation_contract` object:

```json
{
  "schema_version": "1.0",
  "unit_id": "unit:component:91af...",
  "allowed_fact_node_ids": ["symbol:..."],
  "allowed_evidence_ids": ["E1", "E2"],
  "required_fields": ["title", "summary", "responsibilities", "concepts", "relationships"],
  "content_constraints": {
    "max_title_chars": 120,
    "max_summary_chars": 1200,
    "max_responsibilities": 12,
    "max_concepts": 24,
    "max_relationships": 48
  }
}
```

The calling agent must:

- use only returned Evidence;
- cite Evidence IDs on every semantic claim;
- reference only allowed fact node IDs;
- avoid adding raw source text beyond short identifiers already present in Evidence;
- submit one complete unit document.

The contract is data, not a prompt. The caller may use any model or no model at all.

## 11. Semantic Submission Validation

Command:

```bash
repo-dive graph unit <repository> \
  --unit <unit-id> \
  --input unit.json \
  --format json
```

Validation order is stable:

1. decode exactly one JSON document;
2. validate schema version and unknown fields;
3. validate repository and index identity;
4. validate unit existence, kind, and current state;
5. validate membership and Evidence snapshot hashes;
6. validate scalar lengths and collection limits;
7. validate fact-node and concept references;
8. validate Evidence IDs on every semantic statement;
9. validate semantic relationship endpoints and kinds;
10. calculate the canonical submission hash;
11. apply idempotence rules;
12. persist state atomically.

Idempotence:

- same unit + same membership hash + same snapshot hash + same submission hash: success with `unchanged: true`;
- same generated unit + different submission hash: `graph_unit_already_generated`;
- stale snapshot or membership: `graph_evidence_stale`;
- concurrent state change detected by expected state hash: `graph_state_conflict`.

Version 1 does not provide an overwrite flag. Regeneration requires a separately designed reset/invalidation command.

## 12. Projection Contracts

### 12.1 Architecture view

```json
{
  "component_ids": ["component:..."],
  "dependency_edges": [
    {
      "source_component_id": "component:...",
      "target_component_id": "component:...",
      "fact_edge_ids": ["edge:..."],
      "evidence_ids": ["E1"]
    }
  ],
  "entry_component_ids": ["component:..."],
  "content_hash": "sha256:..."
}
```

Component membership and dependency direction are deterministic. Titles, responsibilities, and explanatory relationships come from validated semantic units.

### 12.2 Flow view

Each flow contains:

- deterministic root, steps, and fact edges;
- agent title and summary;
- per-step explanation with Evidence IDs;
- static-analysis coverage and truncation flags;
- related component IDs.

The view must not label a static flow as a guaranteed runtime trace.

### 12.3 Reading tour

The deterministic order uses:

1. repository and manifest overview;
2. entry components;
3. dependencies before dependants when acyclic;
4. stable strongly connected group ordering when cyclic;
5. test and extension scopes after their production scopes;
6. stable scope ID as final tie-breaker.

The calling agent supplies evidence-cited rationale for each stop but cannot reorder the tour in Version 1.

### 12.4 Wiki topics

Wiki topics are advisory records:

```json
{
  "id": "wiki-topic:graph-evidence",
  "title": "Evidence-grounded graph generation",
  "summary": "...",
  "component_ids": ["component:..."],
  "flow_ids": ["flow:..."],
  "relevant_files": ["src/repo_dive/context/packer.py"],
  "evidence_ids": ["E1", "E4"]
}
```

They are not Wiki page definitions. The governed template registry still owns page IDs, heading structure, locale, and direct source paths.

## 13. CLI Contract

### 13.1 Commands

```bash
repo-dive graph init <repository> \
  --node-budget <count> \
  --edge-budget <count> \
  --locale en|zh-CN|ja \
  --format json|markdown

repo-dive graph evidence <repository> \
  --unit <unit-id> \
  --token-budget <tokens> \
  --max-results <count> \
  --format json|markdown

repo-dive graph unit <repository> \
  --unit <unit-id> \
  --input <path|-> \
  --format json|markdown

repo-dive graph status <repository> --format json|markdown
repo-dive graph validate <repository> --format json|markdown
repo-dive graph build <repository> --format json|markdown
```

`--node-budget`, `--edge-budget`, `--token-budget`, and `--max-results` are positive integers. They have no implicit unbounded value.

### 13.2 Success envelope

Every JSON command emits exactly one document:

```json
{
  "schema_version": "1.0",
  "command": "graph.status",
  "repository": ".",
  "result": {}
}
```

The `repository` value is a normalized presentation value and must not reveal host-specific absolute paths when the command can identify the repository as `.`.

### 13.3 Error envelope

```json
{
  "schema_version": "1.0",
  "command": "graph.unit",
  "error": {
    "code": "graph_evidence_stale",
    "message": "The persisted Evidence no longer matches the current index.",
    "details": {
      "unit_id": "unit:component:91af...",
      "recovery": "Run graph evidence for this unit again."
    }
  }
}
```

Stable error codes:

| Code | Exit | Meaning | Recovery |
|---|---:|---|---|
| `graph_invalid_input` | 2 | Invalid flags or JSON | Correct input; do not retry unchanged |
| `graph_budget_insufficient` | 2 | Required graph facts cannot fit | Raise explicit node/edge budget |
| `graph_required_evidence_budget` | 2 | Required chunks cannot fit | Raise token budget |
| `graph_unit_already_generated` | 2 | Different payload for completed unit | Preserve current unit; use future reset workflow |
| `graph_state_conflict` | 2 | Working state changed concurrently | Read status and retry from current state |
| `index_not_found` | 3 | No published index | Run `repo-dive index` |
| `index_stale` | 3 | Source differs from index | Rebuild index, then run `graph init` |
| `graph_not_initialized` | 3 | No graph state | Run `graph init` |
| `graph_evidence_stale` | 3 | Unit Evidence no longer current | Recollect Evidence |
| `graph_incomplete` | 3 | Required units are not generated | Inspect `graph status` |
| `graph_validation_failed` | 3 | Persisted state violates contract | Preserve artifact; correct reported unit/state |
| `graph_write_failed` | 4 | Atomic persistence failed | Surface diagnostic; preserve last valid artifact |

Error messages are safe summaries. Source contents and stack traces go neither to the JSON result nor routine stderr.

## 14. Freshness and Incremental Reuse

### 14.1 Hashes

Canonical JSON uses UTF-8, sorted object keys, compact separators, normalized POSIX paths, and stable ordered arrays. Content hashes exclude timestamps and transient diagnostics.

Required hashes:

- fact graph hash;
- per-component membership hash;
- per-flow membership hash;
- per-unit Evidence snapshot hash;
- per-unit semantic submission hash;
- projection hashes;
- final artifact hash.

### 14.2 Reinitialization

`graph init` compares the current published index with graph metadata.

- Same index identity and same budgets: return `unchanged: true` without rewriting state.
- Same index identity and larger budgets: rematerialize facts, create new units, and preserve still-valid units.
- Changed index identity: rematerialize facts and compare unit membership and Evidence item content hashes.
- Smaller budgets: require explicit acceptance through the supplied budgets; units that lose referenced facts become stale.

Semantic reuse is allowed only when all of these are unchanged:

- unit kind and subject identity;
- membership hash;
- referenced fact-node content;
- Evidence snapshot content;
- semantic schema version.

Otherwise the unit becomes `stale`.

## 15. Persistence and Concurrency

- All writes use temp-file plus atomic replace in the selected repository.
- State mutation compares an expected prior state hash before replace.
- A mismatch returns `graph_state_conflict`; it never merges silently.
- Publication validates from a single immutable state snapshot.
- A crash before replace leaves the previous state or artifact valid.
- A crash after replace yields either the previous or next complete document, never a partial file.

No lock service or daemon is introduced. File-level optimistic concurrency is sufficient for Version 1.

## 16. Security Boundaries

Always:

- resolve and validate the repository root before reads or writes;
- reject absolute artifact paths and path traversal;
- validate stdin as exactly one bounded JSON document;
- enforce scalar and collection size limits before expensive processing;
- keep source chunks only in local Evidence/state artifacts;
- return safe diagnostics.

Ask before changing:

- the private index schema;
- dependency lists;
- the Wiki template contract;
- parser relationship semantics;
- CI configuration.

Never:

- call a model implicitly;
- execute repository code to infer flows;
- follow paths outside the selected root;
- treat agent text as instructions to the CLI;
- allow agent submissions to create parser facts;
- overwrite a valid published artifact after a failed validation.

## 17. Code Style and Model Pattern

Use immutable, typed values and explicit decoding at the input boundary:

```python
@dataclass(frozen=True, slots=True)
class FactEdge:
    id: str
    source_id: str
    target_id: str
    kind: FactEdgeKind
    origin: FactOrigin
    confidence: float
    provenance: EvidenceLocator


def decode_unit_submission(value: object) -> UnitSubmission:
    """Decode one untrusted JSON value or raise GraphValidationError."""
```

Conventions:

- public and internal interfaces are type annotated;
- domain objects are immutable;
- decoders reject unknown fields;
- sorting is explicit at the producer boundary;
- no model contains filesystem or terminal behavior;
- enum values and stable error codes use lowercase snake case;
- repository paths are POSIX strings, never `Path` values in public JSON models.

## 18. Testing Strategy

### 18.1 Unit tests

- public ID stability and collision handling;
- canonical JSON and hash stability;
- strict schema decoding and unknown-field rejection;
- deterministic budget inclusion and truncation reasons;
- component and flow derivation fixtures;
- Evidence required-before-supplemental behavior;
- semantic citation and referential-integrity validation;
- state transitions and idempotence;
- projection ordering and cycle handling;
- source identity and incremental invalidation.

### 18.2 Integration tests

- full `index -> graph init -> evidence -> unit -> validate -> build` flow;
- stdin submission and exactly-one-JSON stdout;
- exit-code and stable-error mapping;
- interrupted or failed write preserves the previous artifact;
- stale index and stale Evidence recovery;
- partial graph publication with visible truncation;
- existing Wiki workflow remains unchanged.

### 18.3 Evaluation fixtures

Add small repositories with known architecture and flow truth:

- a linear Python CLI flow;
- a cyclic component dependency;
- a repository with no supported entrypoint;
- a repository larger than the supplied budgets;
- a mixed-language repository with incomplete relationship coverage;
- a source edit that affects only one semantic unit.

Every new graph heuristic requires a fixture demonstrating the intended improvement and absence of unsupported relationships.

### 18.4 Required verification

```bash
make setup
make check
make test-unit
make test-all
```

Focused test commands may be used during TDD, but completion requires `make check` and `make test-all` from a freshly prepared environment.

## 20. Compatibility and Migration

- Knowledge Graph Schema 1.0 has its own decoder and version field.
- Existing repositories require no migration.
- Absence of graph artifacts is valid.
- Existing Wiki state and artifacts remain readable and writable.
- Unknown future graph schema versions fail safely with `graph_schema_unsupported`.
- Version 1 does not maintain two active graph schema implementations; a future incompatible version must include an explicit migration design.

## 21. Alternatives Considered

### A. Let the agent generate the entire graph

Rejected because fact identity, ordering, provenance, and freshness would be probabilistic and difficult to validate.

### B. Store the graph only in SQLite

Rejected because agents and repository tooling need a stable public artifact. SQLite remains the private index implementation.

### C. Add Neo4j or another graph database

Rejected for Version 1 because it adds operational and dependency cost without improving the required local bounded workflow.

### D. Make Knowledge Graph mandatory for Wiki

Rejected for Version 1 because it would break the existing governed workflow and blur ownership between template structure and semantic hints.

### E. Publish only generated Markdown

Rejected because Markdown cannot express strict provenance, identity, state, truncation, or reusable projections reliably.

## 22. Success Criteria

- All PRD acceptance criteria pass.
- Every public input/output and error code in this document has a contract test.
- The fact graph is reproducible from the published index without a model.
- Every semantic claim is evidence-cited and freshness-validated.
- Partial coverage is explicit and machine-readable.
- The last valid artifact survives every tested failure path.
- Existing index, context, and Wiki contracts remain backward compatible.
